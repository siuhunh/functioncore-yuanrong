# AK/SK鉴权性能优化


## 1. Story 整体设计
### 1.1 功能描述
提升组件间AK/SK鉴权性能
### 1.2 场景分析
当前组件间使用AK/SK鉴权，对于每一个发送过来的请求，都会有走一遍鉴权的逻辑，此部分可通过缓存，优化鉴权方式
### 背景补充：
[AK/SK原理](http://3ms.huawei.com/km/blogs/details/7857193)

[Token和AKSK的区别](http://3ms.huawei.com/hi/group/3362635/wiki_5173035.html)

[华为云AKSK使用方式](https://support.huaweicloud.com/devg-apisign/api-sign-algorithm-002.html)

[AK/SK的安全性](http://3ms.huawei.com/km/blogs/details/6451227)

组件间鉴权，更多的是使用AK/SK的方式，生成一个组件间可以互相识别身份的签名串，与常规的AK/SK在网关作用效果有少许区别

### 1.3 方案详细设计
发送方跟接收方同时缓存签名信息，如缓存的签名匹配，缓存有效期内则视为可信，接收方不重新生成签名
## 发送方：
缓存格式： 
```go
map (time)signature 
```
缓存有效期 3min

签名内容 
- 时间戳
- AK
- 请求内容

对于上内容的HMAC之后，放在请求头中传输

发送方在缓存有效期内的所有请求，均使用此签名内容发送数据，缓存失效后，需要构建新的签名，缓存签名的方式和算法不变

实现方式，发送方使用一个线程，定时更新缓存的数据，在发送的时候，只管从缓存中获取数据，这样可解决并发问题

## 接收方：
缓存格式 
```go
map (signature)time
// map 需要有读写并发安全保证
```
缓存有效期 5min(需要可配置) 

发送方发送的时间戳需要注意实时


接收方在接收到请求后，先根据签名在缓存中查找，如果找到，则认为是可信任的请求方，不做校验，如果找不到，则会根据同样的处理逻辑生成签名，做对比，
如果签名一致，则认为可信请求，同时缓存此签名

缓存大小 100

方案优缺点： 

优点：
- 采用缓存的方式，对于请求方鉴权，可以优化一段时间内的性能
- 服务端缓存的实现，能够满足对于非法请求的拦截校验 

异常点考虑： 
- 服务端处理请求的时间差不能大于5分钟，已实现 
- 发送方发送的数据需要实时  ,跟SE对齐可以通过发送方跟接收方缓存的时间的差异来解决，发送方缓存的时间为3min
