#  平台日志优化、解决日志丢失和防爆盘

关联AR:

+ AR.SR.582d725e.004


## 1. Story 整体设计

### 1.1 功能描述

1. 为了解决日志采集和日志绕接的上产生的丢日志问题，主要是配合管理面对于日志未采集，但是进行日志压缩此原因导致的日志丢失问题。
2. 日志防爆盘，主要是防止cff-agent异常，不对日志进行压缩，导致日志文件所在磁盘太大，压爆磁盘。

### 1.2 场景分析

配合管理面解决日志采集和日志绕接的上产生的丢日志问题以及增加日志阈值，防止cff-agent异常不压缩，导致日志文件太大，撑爆磁盘，影响现网环境。

日志优化和日志防爆盘需求依赖于当前的cffagent的采集日志流程，当前日志采集流程如下：
cff-agent中会有两个协程分别用于采集和压缩，两个协程无配合关系，独立进行。

采集协程：每3s，扫描特定路径下有哪些日志，采集当前路径下的日志，记录一个offset，下次再根据offset 和文件大小判断 接着采集。
绕接协程：每30s(可配置)，扫描特定路径下的日志文件，当发现日志文件大于绕接的阈值，当前是20M，即对日志进行拷贝一份，然后清空。对拷贝的日志进行压缩。.

当前这种方式存在以下问题：
当处于绕接阈值时，如果绕接定时任务，先于采集任务，那么必然有部分日志会优先被压缩，导致无法采集丢失。

### 1.3 方案详细设计

1. 日志优化，配合管理面修改，针对日志打印太快，快速达到日志绕接的阈值，在日志绕接协程先将日志压缩，导致日志采集协程采集不到日志问题。主要方案有以下
（1）用户日志文件大小控制，配合cffagent的阈值 ，达到阈值，创建写新文件，新文件的名字当前名字+时间戳，阈值暂定为100M。


2. 日志防爆盘

   调研了当前现有日志开源方案elk的日志采集、存储、显示开源组件流程和log4j2的对于日志存储旧文件的处理。

   （1）elk中也存在长时间不清理，日志爆盘的可能，当前elk官方出了一个工具Elasticsearch Curator，可以定时删除删除日志，或者自己编写脚本定时删除日志

   （2）log4j2的日志滚动策略：

   当满足一定条件(如文件达到了指定的大小，达到了指定的时间)后，就重命名原日志文件进行归档，并生成新的日志文件用于log写入。如果还设置了一定时间内允许归档的日志文件的最大数量，将对过旧的日志文件进行删除操作。
   RollingFile实现日志文件滚动更新，依赖于TriggeringPolicy和RolloverStrategy。
   其中，TriggeringPolicy为触发策略，其决定了何时触发日志文件的rollover。
   RolloverStrategy为滚动更新策略，其决定了当触发了日志文件的rollover时，如何进行文件的rollover

   1. TriggeringPolicy

   RollingFile的触发rollover的策略有CronTriggeringPolicy(Cron表达式触发)、OnStartupTriggeringPolicy(JVM启动时触发)、SizeBasedTriggeringPolicy(基于文件大小)、TimeBasedTriggeringPolicy(基于时间)、CompositeTriggeringPolicy(多个触发策略的混合，如同时基于文件大小和时间)。

   2. DefaultRolloverStrategy
   DefaultRolloverStrategy指定了当触发rollover时的默认策略。
   DefaultRolloverStrategy是Log4j2提供的默认的rollover策略，即使在log4j2.xml中没有显式指明，也相当于为RollingFile配置下添加了如下语句。DefaultRolloverStrategy默认的max为7。
   max参数指定了计数器的最大值。一旦计数器达到了最大值，过旧的文件将被删除。

结合cff-agent的采集和压缩流程，同时根据日志优化方案，日志防爆采用以下方案，
（1）设置日志大小阈值，当前暂定设置为2G，即整个日志的大小上限为2G。----  2G这个指标需要确定一下
（2）设定日志过大滚动策略，每个日志文件为100M，最存20个日志文件，当日志大于20个时，优先创建一个新的日志文件记录，同时删掉第一个旧的日志文件。

声明：理论上只要cff不挂掉，绕接协程正常执行的情况下，不会出现日志堆积的问题，若出现这个cff-agent出现问题，不进行绕接的情况下，大量日志堆积，超过2g，此情况下允许有日志可以丢失，即（2）的丢掉旧的第一个100M的日志。

声明：

1. 对于日志绕接和采集配合引起的日志丢失问题，当前数据面修改完，并不能解决，还需要管理面修改采集和绕接携程的配合后才可以。要确保日志在采集后才能压缩。
2. 多个日志文件可能会出现采集的日志时序乱掉的问题。 ----- 与张睿确认，多个文件，多个线程采集，lts上显示的采集日志可能不是按照时间排序。

当前日志规格确认：

1. **workermanager：阈值为3g**

    其中vpccontroller.log -> 规格1g（此日志由管理面控制）
    worker-manager-interface-.log -> 规格1g
    worker-manager-run.log --> 规格1g

2. **statemanager：阈值为1g**

    其中state-manager-run.log -> 规格1g

3. **functiontask：阈值为4g**

    其中coresdk-run.log -> 规格2g
    functiontask-run.log -> 规格2g

4. **frontend: 阈值为2g**

    其中frontend-run.log -> 规格2g

5. **cache-manager: 阈值为1g**

    其中cache-manager-run.log -> 规格1g

6. **worker: 阈值为2g**

    其中worker-run.log -> 规格1g
    用户日志文件 -> 1g 
    计费日志 -> 打印较少，基本不会到达100M

7.  **runtime:**（runtime各个组件自己打，无法管理）

    runtime-manager-run.log -- 规格1g  -- 函数调用中打印日志很少，基本可以忽略
    各个语言的runtime的日志
    java-runtime.log ， nodejs-runtime.log ， python-runtime.log -> 打印只有在函数加载时候打印日志，调用过程中是不会打印日志，所以必然不会大于100M

对于当前机器由于目前日志挂盘在系统盘，系统盘大小为80g，需要重新挂载一个数据盘，数据盘大小根据规格大致计算如下：
1. 16U的节点  除去task 4U  最多剩余12U 按照最小规格300 128的话 最多 40个pod   -   80G + 4G + 预留20g --- 104g
2. 32U的节点  除去task 4U  最多剩余28U 按照最小规格300 128的话 最多 94个pod   -  188G + 4G + 预留20g --- 212g
