# AR.SR.IR20230630002318.004.001 降成本专项-FunctionTask函数实例动态保活策略

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

为了降低冷启动调用的发生，现有FunctionGraph平台中采用了基于Time-to-live方法的保活策略来缓存函数实例，即当请求调用结束后，空闲实例60s后再释放。该方案实现简单，但是优缺点也很明显，即函数实例的保活时长越长，则冷启动发生概率越低，但函数实例的缓存成本越高，反之亦然。

系统日志的分析结果表明，Serverless函数在资源配置，执行时间和请求调用频率上有较大的差异。然而现有的静态保活策略并没有针对函数的负载特征做进一步的优化设计，而是不加区分地对所有函数统一进行60s的保活，这在很大程度上导致了不必要的缓存资源浪费。

因此，函数实例在保活机制方面还存在着很大的改进空间，能够进一步压缩以降低成本。

### 1.2特性场景分析

（1）场景触发条件：定期（例如每小时）抓取分析现网函数动态数据日志，持久化存储结果用以动态调整动态保活时间

（2）新增FunctionTask热加载配置，随时关闭动态保活机制，恢复默认60s缩容时间

（3）涉及的组件：FunctionTask，Redis

## 2. 特性/功能实现原理

### 2.1总体方案

FunctionTask从Redis内读取需要更改缩容时间的函数名单以及具体的缩容时间，获取到具体信息后读入内存（初步估计上海一五千个函数，长度五千的map[string, int]）

每次计数前获取一次当前热加载开关的最新状态，若状态为关闭，则使用默认60s

### 2.2模块详细设计 

#### 2.2.1 动态保活方案整体设计实现

![image-20230811110034235](http://image.huawei.com/tiny-lts/v1/images/df83826e5a9597cd884ade2394ea3d8a_428x972.png)

1. 热加载配置是否开启动态调整保活时间配置
2. 配置每小时定时协程，定时查询热加载配置
   1. 若禁止动态调整，则使用默认保活时间
3. 若开启动态调整，则每小时下载保活时间数据到内存，保存到map结构体中
   1. 存入内存前，先查看是否是过去两小时的老数据，若为过期数据，使用默认保活时间，清空map结构体
4. 在现有的函数实例缩容逻辑中，若函数实例未接收到请求，则计数器加1，在map内查询是否存在该函数的动态保活时长上限
   1. 若动态调整保活策略被关闭，使用默认60s
   2. 若不存在，使用默认60s
5. 若存在则使用该上限值替换


### 2.3 约束

#### 2.3.1上下游依赖需求

**当前具体的保活策略目前由管理面提供**：当前思路是依据函数请求量信息，请求量越大的函数保活时间越长，最长为60s，请求量越小的函数保活时间越短，最短15s。

**待验证效果后考虑复用、优化或替换该策略。**
