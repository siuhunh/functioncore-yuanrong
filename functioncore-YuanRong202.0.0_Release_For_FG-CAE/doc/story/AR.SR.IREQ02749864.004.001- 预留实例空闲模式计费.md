#  BusProxy支持对闲置模式的预留实例进行计费

关联AR:

+ AR.SR.IREQ02749864.004.001


## 1. Story 整体设计

### 1.1 场景分析

为对成本价格的降低；FunctionGraph现在需要支持预留实例的闲置模式。采用预留实例闲置模式时，当有请求时，请求工作时间按照100%收费，若是没有请求进入，pod处于空闲状态，此阶段时间按照正常价格的20%收费。

### 1.2功能描述

当前代码中已增加预留实例闲置模式，且预留实例的计费统一在worker-manger进行。

现将预留实例计费方式统一在busproxy来计费。沿用之前的单实例多并发的计费方式。现在worker每5分钟，向bus发送计费时间信息，然后bus写到redis中。

**预留实例非空闲模式**：计费和原来在worker-manger的计费方式保持一致。pod被拉起来开始计费，pod被释放停止计费。

**预留实例空闲模式：**记录整个pod被拉起和被释放的整个时间段，增加空闲时间和工作时间字段，工作时间字段，从第一个请求进来开始计时。到最后一个请求处理完，整个过程的时间段记为工作时间段，空闲时间 = 总时间 - 工作时间。其中工作时间正常计费，空闲时间按照正常计费的20%收取。

   当前方案中会有计费误差，取决于切换的频率，同时五分钟内多次切换不生效只去最后一次，不考虑频繁切换。一次切换最大误差一个周期5分钟。


针对worker-manager与worker就发送空闲模式失败异常场景分析：

1.  worker-manager 通知 worker 失败异常情况
2.  worker挂了重新拉起，重新发送。
3.  worker-manager 挂了，重新起来。

   对于以上三种异常场景增加以下措施：

1. 针对worker-manager 通知 worker 假如失败异常情况，协程中一直会轮询重试，当在通知失败的情况下，切换模式，则cancle掉之前重试携程，重新按照新设置的模式重试，重试次数达到10次，增加告警通知，当检测到全部预留实例都是发送成功，则消警。

2. 针对 worker挂了重新拉起的情况，worker挂掉会重新拉起一个新的pod，特化请求也会一起将空闲模式一起发送过去，如果发送失败，说明特化请求失败。所以新拉起来的worker，一定是发送成功的，后续假如发生发送空闲模式请求失败的情况，则参照措施1。
3. 针对worker-manager 挂了，重新被拉起来的异常情况，worker-manager读取etcd中/instance/ key 下的数据，查看有哪些是预留实例，读取当前的模式，重新发送当前模式的请求到各个预留实例中，发送策略采用上述1中的流程。

重试流程：

1. 增加发送本地缓存，缓存预留实例发送失败的信息存放在map中key为podName。采用time.AfterFunc进行重试
2. 每次重试前，优先查阅一下workermanager中缓存中实例是否存在，不存在则从本地失败map中剔除，不进行重试直接return
3. 当在发送失败重试流程中，发生空闲模式切换，则新的空闲模式请求发送前，会cancle掉之前的旧的空闲模式重试，在发送新的空闲模式请求。

### 2.4 可靠性（Reliability）

1. functionbus 异常重启 functionbus 异常重启，worker上报并发资源占用时长请求会失败，上报失败不丢失数据，保留到下一次一并上报。
2. redis 一段时间不可用 当 redis 一段时间不可用，functionbus 响应返回失败错误码，worker 收到响应错误码为失败时，不丢失上报数据，保留到下一次一并上报。
3. 持续未上报成功 因为并发资源占用时长数据会进行二次聚拢，所以每次上报只有一条时长窗口数据，持续一小时未上报成功也就12条数据，一条数据占用24byte数据 所以worker200M内存，分100M内存用于存储时间窗口数据，支持连续15170天数据持续未上报成功。
4. worker 和 runtime-manager 异常 当 worker 和 runtime-manager 异常函数实例会退出，在优雅退出阶段进行最后一次并发资源占用时长数据上报。 
5. runtime 异常重启场景，资源占用时长如何统计？ 当 runtime 异常重启时，worker 继续接收调用请求并缓存到一个队列。当 runtime 重启成功，将队列中的请求出队处理，出队处理去请求走原先逻辑，不影响资源占用时长的计算。同时缓存队列不进行计费。
7. 极端场景无法上报 （1）redis持续不可用; 一个worker连续15170天数据持续未上报成功，此类场景基本不会出现。 （2）functionBus持续不可用；functionBus不可用，也就没有调用请求到worker，所以也就没有需要上报的资源占用时长。 （3）worker实例直接退出，例如节点机器直接下线场景，导致worker直接退出，未走优雅退出逻辑，无法进行最后一次资源占用时长上报； 如果之前的周期上报成功，则最多丢失默认五分钟的数据，如果之前周期都为上报失败，则会丢失本次上报。
