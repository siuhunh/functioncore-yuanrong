# workermanager启动清理游离pod

关联AR：AR.SR.IREQa2b7bf96.003.013 

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

### 1.2特性场景分析

**1. 背景**

开发01环境在k8s master节点done之后，发现大量自定义镜像实例，没有被打标签。workermanager重启之后，无法正常纳管相关实例，无法正常调度，无法正常回收，导致资源被消耗，进而暴露该问题。

**2. 现状分析**

基于开发01问题场景梳理代码，发现特化实例流程如下：

[workermanager特化打标签](https://cloudmodeling.tools.huawei.com/projectspace/detail/2928afd8ae624e609af7b0148bf05fad?projectDiagramUUID=2a807d9bb0b744ef82b3bd33e1945d39&versionUUID=)![workermanager特化实例打标签流程](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/3NXg?t=1675820634197)

如图：workermanager在选择到实例后，会先打一次标签，核心标签：isPoolPod=false。在完成特化后，会打一次标签：函数元信息等相关数据。打标签当前都是**异步执行**的操作，两次打标签均成功后，才会写入etcd，供上层发现。

打标签失败场景下核心问题点分析：

1. 选pod时打标签失败，isPoolPod=true。**k8s定期会推送实例事件，workermanager会去处理**。基于此背景，实例被特化之后，标签打失败，isPoolPod=true。k8s下一次推送这个实例时，由于isPoolPod=true，会被重新加到pool池调度，**导致重复特化，导致实例crash**。

2. 完成特化时打标签失败，isPoolPod=false。**workermanager根据k8s事件，isPoolPod=false时，解析标签构建实例信息，写etcd**。基于此背景，虽然实例被标记是被选择特化的pod，但是由于标签内没有含有任何函数相关信息，无法构建路由信息，无法写etcd，导致上层无法正常发现该实例。

   实例路由未写入etcd的影响分析：

   1. 请求扩容时，返回上层bus纳管，通过反压能够被frontend纳管。但是路由信息未写入etcd，实例被删除时，上层无法感知到删除。如果是预留实例，会不断往该实例调度，返回211406：call request sending error。导致请求无法正常调度。
   2. 组件进行升级，上层组件bus通过etcd重新纳管实例，由于无etcd事件，所以无法纳管。workermanager启动时，判断该实例被特化，但是函数相关标签信息均为空，写etcd事件后也无法正常被上层bus纳管，无法缩容，导致游离。

3. 选pod时，完成特化时，打标签均失败。上述问题均会存在。

## 2. 特性/功能实现原理

### 2.1总体方案

基于当前现状下分析的核心问题，内部优化改造方案如下：

1. 选择pod后，打标签改为同步。如果打标签失败，直接返回错误，认为该次扩容请求失败。
2. 路由信息写etcd改为特化pod完成后即写，保证一个实例如果被调度，etcd里面一定有信息，实例能够被上层调度组件纳管。
3. 启动时清理游离pod。按照新的机制实现以后，游离的pod只有特化完成后打标签失败的pod。workermanager启动后，依据标签判断：isPoolPod=false, specialize=prestart。认为是游离状态的pod，从而进行删除，不纳管。启动时，发现etcd有数据，该实例不纳管，会将etcd路由信息删除。上层调度组件发现，驱逐实例。
4. 打标签动作当前都是直接使用context.TODO，没有设置超时时间，增加10s超时时间。
