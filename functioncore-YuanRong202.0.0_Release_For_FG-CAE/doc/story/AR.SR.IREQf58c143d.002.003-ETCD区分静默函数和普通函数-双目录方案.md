# 函数区分静默函数和常用函数

关联AR：

* ARID：AR.SR.IREQf58c143d.002.003 

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

**需求背景**

* 目标：收编 v1 函数，函数量级10w+，未来扩容预估40w+。要求对 ETCD 无压力，对组件内存无负载。
* 当前限制：
  * frontend，functionbus，cache-manager，workermanager 在启动时均会对 ETCD 做全量查询。10w函数单次查询会对 ETCD 造成 400MB 左右的内存压力，造成 ETCD 内存和节点网卡流量负载。
  * workermanager 需要缓存函数的全部信息，单条函数内存占用 4KB。从函数的实际使用上面来看，现存函数(v1)很多很久没有被使用过，都进行订阅的话对 workermanager 内存也存在无效占用。

### 1.2特性场景分析

主要场景：

1. v1 函数收编时，需要将数据全部同步到 ETCD，会在短期产生大量的函数事件。由于组件内需要对这些事件进行处理，会造成组件负载，影响正常调用的性能。

2. v1 函数收编之后，函数暴增。组件启动时，都会对这些函数进行全量查询获取，对 ETCD 会造成负载。

   ETCD 负载的点：

   * 内存负载，无法快速GC。
   * 节点网卡负载，需要返回大量函数数据给组件处理。

## 2. 特性/功能实现原理

### 2.1总体方案

* 管理面

  1. 需要识别区分静默函数和常用函数，识别维度：(每日巡检)

     * 一个月内无计费信息，计费产生：调用、预留实例。

       * 被调函数计费需求：AR.SR.IREQ29c81f63.001.001。——史宏宇。

     * 一个月内函数未发生更新。

       ...

       具体维度需要管理面同事分析。

  2. 所有函数ETCD key-prefix：/silent/sn/functions/-。常用函数会写/sn/functions-。数据面组件当前会根据 key 前缀去订阅和获取函数，静默函数前缀只有 /silent，数据面不会去订阅相关数据。

  3. v1 函数收编时，将数据都认为是静默函数，当产生调用或更新的时候再将其更新为常用函数。防止v1收编时产生大量的函数事件，造成组件负载。区分识别常用函数，静默函数。静默函数只写/silent/sn/functions， 常用函数sn/functions- 和 /silent/sn/functions- 均需要写。

* 数据面

  函数调用到达数据面时，如果缓存未命中，需要向ETCD进行查询。

  * 查询/silent/sn/functions，更新至本地。

### 3.4可靠性（Reliability）

*【在给定的条件、给定的时间区间能无失效地执行要求的能力】*

1. 当前方案下，如果后续产生大量的函数(/sn/functions目录)，问题仍然会存在。

   预防：在做组件更新时，需要先确定对应region etcd /sn/functions目录的函数数量。

2. 函数运行过程中(函数存在调用，或存在预留实例)，被切为静默函数。数据面只订阅/sn/functions目录，所以会感知到删除事件，存在波动：实例退出，调用返回函数更新。请求再进来时，通过/silent目录查询更新缓存。

3. 一个静默函数，产生了调用。数据面通过向ETCD /silent目录查询缓存了函数信息，执行调用。但是无法感知函数删除事件，缓存常驻。

4. 特化流程，cache-manager下载代码缓存未命中，不能影响主特化流程。

### 3.9性能

*【评估需求本身的性能影响、对其他流程的性能影响】*

### 3.10资源

*【评估需求对资源的占用，例如go协程，文件句柄、内存、cpu】*

ETCD需要全盘存储所有函数当做静默函数，还需全盘存储常用函数，极端情况下所有函数都是常用函数，数据存储会扩充至两倍。

其他逻辑客户无感知。
