# Workermanager请求优先级队列 ，优先处理首次特化请求

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

该需求为内部的可靠性增强：在资源不足的情况下，优先部署首次特化的函数。

### 1.2特性场景分析

1. 当前workermanager处理函数特化请求时，是并发的、不区分优先级的。如果有用户函数大量触发弹性扩容，耗尽pod池，即便pod池补充上来也被该函数消耗，这样就可能导致其他用户的函数完全无法部署实例。

2. 基于上述场景继续分析，同时有弹性实例请求和首次特化请求过来，而当前资源只够特化出一个pod；如果先处理弹性请求，则首次特化的函数调用一定会失败；而如果先处理首次特化实例，由于弹性请求的函数本身就有实例，在functionbus 40s排队时间超时前，该请求仍有机会被处理从而执行成功。

因此，需要在workermanager中区分请求的优先级，优先处理首次特化的请求。

## 2. 特性/功能实现原理

### 2.1总体方案

workermanager的所有pod特化请求，都需要先通过podfetcher的GetPod接口，从poolmanager里获取可用的pod，之后才会实际进行函数特化流程。这里获取pod是一个并发抢占的过程。

优先级队列会添加在获取pod这一步，在poolmanager调用内部getPodInternal时，先将请求Add进队列中，通过Wait接口等待队列调度通知，再进行后续流程。

同时，原先的流程中，podfetcher在请求poolmanager之前，会到cache中计算函数是否到达最大实例；现在cache会在校验最大实例的同时返回，该请求是否是函数的首个实例，方便后续的优先级计算。

优先级定义：

预留实例>首次部署的实例>弹性实例

优先级计算方式：

1. 若为预留实例，则优先级最高；

2. 函数cache里会维护当前函数已有实例数和正在拉的实例数，如果已有实例数+正在拉的实例数 = 0，则说明是首次部署的函数实例，优先级居中；

3. 其余请求为最低优先级

- - 分两点考虑：1. 其他实例不可用的前提是pod池持续被消耗完，而预留实例的重拉是有指数回退的，后续重试的等待时间会来到30s，影响可控；2. 当前预留实例拉不起来会有紧急告警。

### 3.8可测试性

*【代码本地LLT易测试、针对外部接口测试、测试用例具有稳定性】*

本特性的主要功能点在于调度的优先级；测试的主要难点在于，请求到达队列的顺序会影响实际调度结果，而直接构造并发请求实际上无法确保每个请求到达的先后顺序；

对于LLT，内部的一些执行顺序可以通过延迟调用接口、sleep等手段构造，且用例结果能保证稳定；

对于ST等更高级别的用例，由于无法保证函数特化请求到达workermanager的顺序，需要构造pod池资源不足的场景，保证同一时刻所有的特化请求都阻塞在workermanager的队列中，这样才相对容易观察实际的调用顺序。

### 3.9性能

*【评估需求本身的性能影响、对其他流程的性能影响】*

在原有的pod挑选流程上增加了一个优先级队列，性能肯定会有所下降；从实际测试特化pod来看基本没有差别；增加benchmark的LLT用例对比前后性能，高并发下选取pod 的时间从600纳秒上升到2800纳秒，在整个pod特化的流程中应该可以忽略不计。

### 3.10资源

*【评估需求对资源的占用，例如go协程，文件句柄、内存、cpu】*

每种规格的pod池都会新增一个协程用来调度优先队列。目前一个有15种pod池规格，所以增加了15个协程；在没有对应规格的pod请求时，协程会在sync.Cond.Wait()处挂起；对资源的影响可控。

不涉及兼容性改动；优先级调度功能默认开启，可通过配置关闭。该配置可热加载，配置项为workermanager的configmap中poolMgrConfig.disablePriorityQueue，默认为0或者不填，填其他大于0的数字则关闭优先级队列功能；填小于0的数字或其他值不合法。
