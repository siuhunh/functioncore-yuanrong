# AR.SR.f3bf3df5.001 【服务依赖】元ETCD故障，不影响服务运行与重启

## 1. 需求场景分析

场景：当前元数据ETCD故障，组件发生重启，初始化时会因为无法与元数据ETCD建立连接导致无法正常启动

### 1.1 特性需求来源与价值概述

需求来源：服务依赖降级场景下，外部依赖故障，业务组件不能主动退出（当前不具备），且需要能够正常启动，由于依赖异常，可以功能降级

价值概述：系统可靠/可用/韧性加固，保证在元数据ETCD异常时，业务组件能够正常启动，并且持续上报异常的告警，保证基本的函数功能

### 1.2特性场景分析

1、当前组件正常启动后，若元数据ETCD出现异常，组件无法正常访问，则组件会进行重试连接，同时产生告警，若组件在此期间异常重启，则无法正常启动
2、frontend、bus-proxy、worker-manager、cache-manager、faas-scheduler、state-manager均涉及与元数据ETCD的交互
3、该需求需要保证，元数据ETCD异常时，上述组件发生重启后仍能正常启动，同时产生告警
4、组件正常启动后，基本的函数调用功能需要保证，为此需要依赖函数元数据信息在本地持久化（已有需求实现）
5、组件与元数据ETCD重连成功之前，暂时使用节点本地缓存的元数据保证基本功能，重连成功之后，重新刷新并构建缓存数据

## 2. 特性/功能实现原理

1. 组件正常启动后，元ETCD访问异常，则重试连接并产生告警，直至重连：  
    初始化cli时启动健康检查协程：
    go client.keepConnAlive()
    
    协程中周期性检验与ETCD之间的连通性：
    case <-ticker.C:
    	w.checkConnState()
    
2. 组件重启时，元ETCD访问异常，则重试连接并产生告警，直至重连，在重新连接前，从本地获取元数据信息：
    if wc.EtcdCacheConfig.EnableEtcdCache {
    	err = wc.DoDiffSync()
    }

3. 重试连接成功，告警清理，并重新构建缓存

4. 各组件访问元数据ETCD功能说明：

1、Frontend：
有状态，因为状态路由是写到元数据etcd的，frontend又支持有状态直接调用
并发度，判断是否要向faas-scheduler发请求
注册frontend实例，下沉架构rdispatcher要用，并且是续租模式
支持动态资源配置的功能，如果header里没有资源数据的话，从元数据里获取

2、bus-proxy：
异步请求取消cancel
注册functiontask实例，有状态多集群调度需要，获取状态路由
支持动态资源配置的功能，获取CPU和内存
获取并发度
获取是否是有状态函数
获取是否是bridge函数

3、worker-manager：
函数元数据信息
函数实例数量配置信息
租户委托信息
vpc相关信息

4、state-manager：
状态路由数据

5、cache-manager：
函数元数据信息

6、faas-scheduler：
函数元数据信息

### 2.3 约束

1、由于vpc-controller也依赖元数据ETCD，10月份迭代管理面暂未基线相关依赖降级需求，因此worker-manager组件只能在黄区进行测试验收
2、本地节点只缓存函数元数据信息，因此委托、有状态等功能均会降级，无法保证正常使用，只保证最基本的函数调用

#### 2.3.1上下游依赖需求

AR.SR.ec733c2f.001 bus-proxy初始化对元ETCD负载优化

#### 2.3.2其他约束

若本地不存在缓存数据，则默认无元数据信息
