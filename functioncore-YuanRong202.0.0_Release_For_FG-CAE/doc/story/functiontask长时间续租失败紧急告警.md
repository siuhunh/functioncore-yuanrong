# FunctionTask长时间续租失败紧急告警

## 1.需求场景分析

### 1.1特性需求来源与价值概述

需求来源于内部可靠性改进。

etcd租约（Lease）是一种检测客户端存活状况的机制。如果 etcd 群集在给定的 TTL 时间内未收到 keepAlive，则租约到期。当租约到期或被撤销时，该租约所附的所有 key 都将被删除。

当前Functiontask使用etcd租约机制来发布服务。

在etcd压力大响应慢、etcd网络故障等场景下，FunctionTask向Etcd续租会失败

续租失败之后，函数请求不会被调度到续租失败的Functiontask上，但是FunctionTask节点上的预留实例一直存在，就会出现预留实例收费但是不工作的场景。这种场景不合理，但是用户比较难感知，因为当前实例个数指标已经移除。

当前functiontask每隔10s检测一次与etcd的连接，如果检测连接失败，会上报重要告警。这个能覆盖一部分续租失败的场景。但从现网运维实际来看，重要告警经常被忽略。

因此，针对长时间续租失败的情况，需要通过紧急告警来通知运维人员介入处理。

### 1.2特性场景分析

特性在FunctionTask向etcd长时间续租失败的场景下起作用。当Functiontask检测到一段时间内向etcd续租均失败后，触发告警，通知运维人员介入修复问题

[functiontask续租场景](https://cloudmodeling.tools.huawei.com/myspace/diagram?diagramId=242923e2b65b4b93a4720c9839e4c76a)

![functiontask续租场景](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/2Fww?t=1657616883156)

1.FunctionTask向路由etcd建立连接后，会启动续租，TTL8s（通过环境变量配置）

2.租约协程每隔4s（通过环境变量配置）向etcd触发一次续租请求

3.如果续租失败，则重新建立租约

## 2. 特性/功能实现原理

### 2.1总体方案

[续租失败告警](https://cloudmodeling.tools.huawei.com/myspace/diagram?diagramId=e73aa1fa58104176a4d89967f5c032b2)![续租失败告警](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/2FxD?t=1657685096763)

1.根据每次续租结果判断续租是否成功

2.如果指定时间内（（通过热加载配置））内续租均失败续租失败，则向OMSVC发送FunctionTask续租失败告警

3.之后如果重新续租成功，则清除续租失败告警

### 2.2模块详细设计

#### 2.2.1模块实现

当前functiontask已支持向omsvc告警，只需要新增告警即可

长时间续租失败告警详情

```
ResourceID：functiontask-routerETCDLease
Cause：etcd lease failed for xxx
告警等级：紧急
续租失败持续时间：10分钟
```

紧急告警的好处是会及时得到处理，风险是如果误告警，告警频繁上报和清除，对运维的压力很大。当前数据面的告警都是重要告警，无紧急告警。

重要告警从现网运维来看，运维关注的比较少。

#### 2.2.2模块类设计

[lease_alarm](https://cloudmodeling.tools.huawei.com/myspace/diagram?diagramId=2b03748fe22d41b5a71de95467b8e2e5)![lease_alarm](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/2G1v?t=1657624762390)

1.functiontask的etcd续租在etcdRegister中实现，etcdRegister初始化时创建续租alarm

2.在etcdRegister中新增monitorLease方法，用于监控续租

3.当续租失败超过1分钟（可热加载配置）时，调用alarm的ReportAlarm方法上报告警，再次续租成功时，调用ClearAlarm清除告警

4.defaultAlarm封装了已有OMSVC告警的实现

### 2.3 约束

#### 2.3.1上下游依赖需求

无，FunctionTask当前已支持告警能力，无需管理面适配修改，确定告警详细后，知会孔凯霆

#### 2.3.2其他约束

1.如果在告警恢复清除前，FunctionTask重启，此时告警无法自动清除，需要手动清除。目前数据面所有的告警都是这样，重启后无法自动清除

### 3.4可靠性（Reliability）

*【在给定的条件、给定的时间区间能无失效地执行要求的能力】*

1.Register告警上报到公共告警模块机制：

​	持续续租失败10分钟，向公共模块发送告警。

​	持续续租失败，没隔10分钟向公共模块发送告警

2.公共模块告警机制：

​	第一次告警上报时，向omsvc上报告警，如果告警没清楚，告警不再重复上报

​	向omsvc告警上报又清除，在之后的30分钟内，业务模块若告警，每10次告警上报一次告警到omsvc

​	向omsvc告警上报又清除，距离上一次告警的30分钟内业务模块没有告警，则上报一次告警到omsvc

3.etcdRegister不感知告警成功或失败，告警功能不影响续租功能
