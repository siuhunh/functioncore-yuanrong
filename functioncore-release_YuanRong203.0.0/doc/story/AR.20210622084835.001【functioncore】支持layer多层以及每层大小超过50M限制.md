# AR.20210622084835.001【functioncore】支持layer多层以及每层大小超过50M限制

关联AR:
+ ARID1: AR.20210622084835.001

## Story 整体设计

### 功能描述
当前layer限制只支持不超过5层以及每层大小不超过50M，需要调整以适应客户最新需求。

### 场景分析
金融风控VaR计算下，layer层需要存放依赖的第三方库和计算模型，原本配置的5层/50M不能满足需要。经评估，金融场景需要支持配置为8层/100M

### 方案详细设计

#### cli 最大支持layers数可配置

原yrctl cli命令固定只支持5层及以下的layer，在cli.resource.function.json中新增配置项maxLayersSize（若不配置默认为5）。根据用户配置参数支持部署包含对应layer层数的函数，最大不超过20。

#### 调整函数与layer配置

+ 当前配置

  ```
    zipfile:
    	ZIP_FILE_SIZE_MAX_MB: 50
      UNZIP_FILE_SIZE_MAX_MB: 100
      FILE_COUNTS_MAX: 30000
      DIR_DEPTH_MAX: 20
  
  # layer limit
    layer:
      LAYER_MAX_NUMBER: 5
  ```

+ 金融场景可配置

  | 配置项                 | 当前  | 配置建议 |
  | ---------------------- | ----- | -------- |
  | ZIP_FILE_SIZE_MAX_MB   | 50MB  | 100MB    |
  | UNZIP_FILE_SIZE_MAX_MB | 100MB | 200MB    |
  | LAYER_MAX_NUMBER       | 5     | 8        |

#### 配置调整后系统配置调整分析

+ worker临时磁盘空间&内存

  + 当前worker最小配置临时空间500M，内存200M。
+ 流式解压函数包，解压后的数据直接放在磁盘中，worker当前内存配置已可满足。
  + 临时存储空间由于layer包与函数包变大，增加ephemeralStorage limit默认配置为2G，以便pod按需获取存储资源，通过配置文件ephemeralStorage项可更改limit ephemeralStorage的值。

+ 超时时间配置

  + podGeneralizeTimeout：需要下载的压缩包扩大至900M（function+8*layer），函数特化超时时间做相应调整。
  
  > 以1G带宽为例，建议按照15M/s的时间配置，修改后总代码包900M，配置为70s:900/15 + 10s建立通信与其他流程处理时间
  
  + requestWorkerTimeout：建议配置为workermanager特化超时时间+3s
  + WriteTimeout: worker写请求处理超时时间：建议配置与workermanager超时时间保持一致
  
+ 建议配置具体变化如下表格，并可在实际应用场景中按需调整

  | 配置项               | 当前          | 配置建议 |
  | -------------------- | ------------- | -------- |
  | podGeneralizeTimeout | 33S           | 70S      |
  | requestWorkerTimeout | 36S           | 73S      |
  | WriteTimeout         | 33S           | 70S      |
  | ephemeralStorage     | 不配默认为500 | 2048MB   |
