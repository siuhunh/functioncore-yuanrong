## Story 整体设计

### 功能描述
+ *Why: 这个功能的目的    --必要性*

    防止某个租户，无限制的占用实例来运行函数，耗尽集群的实例资源，导致集群无空闲资源响应其他函数请求，影响其他租户的使用体验

+ *Who: 谁来用这个功能   --使用对象*

    该特性在函数页面不对租户直接呈现，只是作为整个系统的一个流控门槛能力，在租户实际正在使用的实例数超限时，进行相应的限制动作

+ *When: 什么时间/背景使用   --使用时间*

    单个租户请求大量下发，实际使用的实例数超限，触发该流控特性

+ *Where: 什么地点使用   --使用地点*

    不涉及

+ *How: 如何使用   --使用方式*

    FG创建函数页面，租户不感知该特性，跟“单函数最大实例数”有差异；
    
    租户最大实例数的默认值由管理面统一指定，并在文档中提前声明&澄清，若租户有个性化需求，管理面提供入口来修改；

+ *What happen: 使用过程中可能影响什么功能   --功能交互*

    租户实际使用的实例数达到上限后，后续的用户调用请求将返回对应的报错/提示信息（报错策略跟“单函数最大实例数”保持一致，错误码需新增并与function-task、文档做配合）

+ *Experience: 用户的体验如何，包括性能安全、韧性、可靠性、可用性、隐私等方面的体验   --体验*

    单租户的体验、可用性有一定程度的下降；所有租户拉通、平台的可用性有较大的提升

### 方案详细设计

#### 现状分析
**关键问题：单租最大实例数是否区分 按量实例、预留实例 来分类管理**

**AWS**

不区分

https://docs.aws.amazon.com/lambda/latest/operatorguide/provisioned-scaling.html

**Ali**

区分，两类实例单独控制

https://help.aliyun.com/document_detail/185038.html

**讨论结论**

跟管理面 洁龙、宗南、方凯，SE春哥 对齐，结论是需要进行区分，即 **租户最大实例数 = 租户最大按量实例数 + 租户最大预留实例数**

+ 租户最大按量实例数由数据面计算、控制

+ 租户最大预留实例数 数据面只计算，真正的控制动作由管理面提前计算并拦截


#### 方案设计
方案示意图：

[单租户最大实例数](https://cloudmodeling.tools.huawei.com/myspace/diagram?diagramId=4738aab6aa4040378c1df245a23a3b8a)
![单租户最大实例数](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/2G4b?t=1658543503552)

1. 管理面下发流控配置
    + 管理面会向各个集群下发租户的默认实例数配额配置
    + 若租户有差异化修改配置的动作，管理面需将指定租户的“单租户最大实例数”配置写入etcd
    + 此配置区分租户、区分集群

2. 数据面维护tenantCache缓存
    + 管理面一开始只会往etcd里下发一条单租户最大实例数的默认配置(见etcd key示例)，worker-manager主节点启动后，会去获取这个key，若失败，则用本地默认配置(按量实例、预留实例各1000)
    + 新增tenant cache，用来记录租户的实例数quota、实例数当前统计值；
    + 通过etcd事件驱动，感知管理面对租户实例数quota的调整，进而驱动修改tenant cache中的quota上限值；
    + 通过统一接口，收编worker-manager中对function cache中实例数计数进行修改的地方，进而驱动tenant cache中对应租户当前实例数的增加。如此，将实例数计算的时间分摊，有利于统一入口流控时的计算性能提升；
    + 通过定时任务，根据function cache来校准tenant cache，防止异常场景设计点3带来的offset偏差，达到一个准确性、性能的折中；

3. 数据面流控
    + 当特化请求进入时，除了校验“单函数最大实例数”(已有逻辑)前，还会进行“单租户按量实例数”、“单租户预留实例数”校验
    + 校验逻辑会读取tenantCache中租户对应的tenantInstanceInfo，直接读取相关字段，与上限值比较
    + 若租户普通实例数超限，则请求会倍拦截，并返回ReachMaxOnDemandInstancesPerTenant 150432，报错策略与单函数实例数超限一致，先排队再报错
    + 若租户预留实例数超限，只会进行warn日志打印，不做真正的拦截动作，预留实例的流控由管理面负责
    + 若流控校验都失败，报错优先级 “单租户按量实例数” > “单函数最大实例数”
    + 若租户实例数quota在etcd中被置为-1，则跳过租户级流控，避免极端异常场景下，影响租户使用
    

> **tenantCache 数据结构参考**
```
type tenantCache struct {
	// key: tenantID   value: *tenantInstance
	tenantInstanceList sync.Map
}
 
type tenantInstance struct {
    // quota - trigger by etcd tenant key event
	maxOnDemandInstance   int64
	maxReversedInstance   int64
    // on-demand ins, include scaling status - trigger by instance change callback or calibrated by function cache in cycle
	onDemandInsNum        int64
	scalingOnDemandInsNum int64
    // reversed ins, include scaling status - trigger by instance change callback or calibrated by function cache in cycle
	reversedInsNum        int64
	scalingReversedInsNum int64
    // lock
	mux                   sync.RWMutex
}
```

#### 外部交互分析&&上下游依赖需求
1. 管理面对“单租户最大实例数”的管理、配置下发

    + 与“单函数最大实例数”直接在函数配置页面体现不同，“单租户最大实例数”不直接在portal对租户呈现
    + 该配置的默认值需要在文档中对租户进行澄清，并提供手段供租户进行修改 —— 修改手段由管理面提供，初步定ServiceCM
    + 该配置需要精确到租户级，否则无法满足差异化需求
    + 该配置需要区分数据面集群，比如租户A的“单租户最大实例数”为1000，且数据面有3套集群，管理面写key时，需写入租户A在3套集群中的配额依次为300,300,400 保证总和为1000，具体分配策略可根据数据面集群总容量按比例计算得出，租户不感知  —— 计算分配策略先采取均分
> **etcd key示例**
```
默认配置key：
/sn/quota/cluster/cluster001/default/instancemetadata
{"tenantInstanceMetaData": {"maxOnDemandInstance": 1000, "MaxReversedInstance": 1000}}

差异化配置key：
/sn/quota/cluster/cluster001/tenant/7e1ad6a6-cc5c-44fa-bd54-25873f72a86a/instancemetadata
{"tenantInstanceMetaData": {"maxOnDemandInstance": 2000, "MaxReversedInstance": 2000}}
```

2. 管理面自身的场景校验、管理面与数据面的配合增强
    + 若某租户最大预留实例数为1000，其存量函数a配置“预留实例数”为500，若其新建函数b配置尝试设置“预留实例数”为600，那管理面应该直接检验报错 —— 预留实例数控制由管理面负责，数据面只统计不拦截
    + 管理面在请求下发时要考虑策略（当前是均分），避免在单个数据面集群中触发 最大按量实例数/最大预留实例数 到上限，但是其他数据面集群中有大量资源空闲
    
3. 产品文档更新
    + 对“单租户最大实例数”（即 租户最大按量实例数、租户最大预留实例数）的默认值、使用约束、修改方案在文档中进行说明&澄清；
    + 对新增错误码进行说明；
    + 提供租户级实例数与函数级实例数配置的最佳实践
    
4. 跟function-task配合
    + 若新增错误码，需跟function-task一起看下，是否有连带修改 —— 确认有适配修改
    + 调研下之前“单函数最大实例数”触发时，报错策略是怎样的 —— 报错策略保持一致，错误码有更新

### 约束
“单租户最大实例数”对租户使用的隐式约束

1. 若租户最大实例数为1000，但是其某个函数中配置“单函数最大实例数”为-1即不限制，则实际能生效的实例数最大也就1000

2. 租户创建函数成功，但是在运行阶段可能会触发流控

3. 偏差澄清：functionCache中的instances属性，与K8S的实际资源有细微的时间差(两者的处理是异步的，即instances若-1，驱动tenantCache计数也-1，但是K8S中的Pod实际删除可能会有一定时间差)，评估可以接受，因为“单函数最大实例数”也会遇到同样的问题

#### 安全性 Security

“单租户最大实例数”由管理面提供标准入口让租户进行修改，安全性可控。

*系统受攻击时保持在有定义的运行状态（包括降级）、遭遇攻击时快速恢复核心系统、受攻击后在业务需要的时间窗内恢复到有效运行态*  

该流控能力对系统韧性有一定的提升。

租户的实例数信息只在内部流控逻辑使用，不对外发布，总体可控。

#### 可靠性 Reliability
*在给定的条件、给定的时间区间能无失效地执行要求的能力* 

worker-manager重启/重新选主后，会重新触发对应租户缓存的生成，保证流控能力持续生效。 

#### 可用性 Availability
*处于按要求执行状态的能力*  

所有租户拉通、平台的可用性有一定程度的提升。

同安全性分析。  

#### 性能 Performance

性能的关键在于对租户缓存的实时更新，在实例数发生变化时，只需对该实例相关的租户、函数的缓存进行更新。

功能自验中，在并发场景下，性能符合预期，流控耗时在微秒级。
