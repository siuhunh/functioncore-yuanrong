# functioncore内存限流场景下有状态调度优化

关联AR:
+ ARID1: AR.SR.857b9694.001
+ 需求来源: 问题单DTS2023050511916转需求

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

1. 普通函数bus内存高位限流阈值(80%)， 有状态高位限流阈值调整至85%。
2. 普通函数低位限流阈值(60%)，有状态函数低位不作限流。

### 1.2特性场景分析

- 目前bus收到handler请求时不会去区分有状态函数和无状态函数，两者按照同一标准对内存进行校验。因为无状态函数已支持集群内部动态迁移而有状态函数目前不支持，所以现需将有状态和无状态的请求进行区分对请求的有状态函数约束条件放宽，减少限流次数。

## 2. 特性/功能实现原理

### 2.1总体方案

1. memMonitor结构体新增属性;

   | **名称**      | **类型** | **默认值**                                   | **描述** |
   |--------------|----------|--------------------------------------------|----------|
   | isStateful | bool      | false | handler请求中的req.IsStateful，需传递至Allow()接口函数内部做判定     |
   | statefulThreshold | uint64      | 0 | 有状态函数的上行阈值，初始化monitor时初始化   |

2. 给monitor.isStateful赋值时使用sync.Mutex{} 锁控制单次请求校验传入修改的monitor.isStateful不会在并发场景下影响其他的函数请求，内存校验完成后恢复默认值；

3. statrfulThreshold在初始化内存控制配置项时 initDefaultMemoryControlConfig() 初始化，默认值为0.85；

4. 有状态函数的低位不做限制，放宽有状态函数的请求条件；

5. 新增封装入口函数 SepMemoryAllowByStateful() 传入请求中的isStateful函数是否为有状态；

性能影响：
1. sync.mutex{}是基于原子操作的互斥锁，性能消耗低。

异常场景：

1. functionbus 异常重启，单个invoke请求失败，集群会重试至其他节点，保留原函数的invoke请求信息；

### 2.3 约束

内存阈值的放宽只针对有状态函数请求
