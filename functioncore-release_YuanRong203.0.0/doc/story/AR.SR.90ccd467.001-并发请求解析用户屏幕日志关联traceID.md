# 并发请求解析用户屏幕日志关联traceID

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

问题单[**DTS2022083017980**](https://dts-szv.clouddragon.huawei.com/DTSPortal/ticket/DTS2022083017980)转需求，背景如下：

容器镜像运行时设置1比10并发，长稳运行 time触发器触发3分钟触发一次 1比10 20最大实例 执行时长15min 发现有概率 有用户日志在一个traceID里打印重复有串的现象，影响用户维测。

不支持context logger的运行时（http、自定义运行时、自定义镜像、go）用户并发调用的话，打印的屏幕日志无法关联到请求id，轮询所有正在处理的请求，将该日志写入每个请求的logRecorder中。

### 1.2特性场景分析

主要实现以下功能：

1. http、自定义运行时、自定义镜像、go用户按照推荐的格式打印日志，能worker能正确解析并关联traceID，推荐的格式为 “时间 traceID 内容”

   推荐格式如下：

   ```
   $utcdatetime(yyyy-MM-dd HH:mm:ss.fff) $requestId $message
   ```

2. 原有http、自定义运行时、自定义镜像、go屏幕日志在并发下会Range打印到全部请求的功能去除。

   例如当前并发数为10，其中一条请求的函数处理逻辑中打印了一条日志，10条请求的Tail log，lts log中都会有该条日志。

   增加FAQ，如果用户没有按照推荐格式打印，日志与traceID，增加如何维测的说明。

   当前代码中此功能已去除，当前非标准打印多并发触发，只在最后一个请求打印出标准输出。

   

3. Rpc类型函数用户如果使用print方式打印推荐的日志格式，也应该能按照上述逻辑解析并关联traceID

   ```
   $utcdatetime(yyyy-MM-dd HH:mm:ss.fff) $requestId [$Level] $message
   ```

4. 推荐日志格式写入资料

### 2.2模块详细设计

根据当前日志场景分两种：

1. 单条日志较小，不会进行日志拆分多条
2. 单条日志较大，会进行日志拆分。

**针对场景1：**

单条日志较小，不进行日志拆分的场景下，

http、自定义运行时、自定义镜像、go用户：最后都是调用WriteStdLog打印日志。

针对功能点1 和 2的修改：

![image-20221013195435473](C:\Users\s00471612\AppData\Roaming\Typora\typora-user-images\image-20221013195435473.png)

若请求数为1，日志可以直接关联，直接打印。

若当前并发请求大于1，则解析日志格式，

1. 若解析成功后找到对应的traceID的请求，将日志打印到对应的请求中。
2. 若解析失败，则走WriteDefaultLog，即多并发场景下，如下traceID  = default， 在请求列表搜索不到该日志，全量日志中可以搜到。

Rpc类型函数用户：

Runtime -》 worker worker接收runtime的rpc请求，调用ProcessLog方法，将日志写到Recorder中，最后通过logRecorder.Finish()落盘

修改worker中打日志代码逻辑，先解析用户的标准输出的日志，若解析成功，获取到用户传入的tarceID，之后找到调用对应的recorder，打印日志。

**针对场景2：**

由于当前针对不同的runtime的单条日志最大限制不同，

第一种： rpc类型的runtime（python、python2、java、nodejs、php、c#）

java 单条日志超过8k会自动换行 ，c# 单条日志超过1k会自动换行，剩余其他语言为90k

第二种：fusion类型的runtime（go、http、customRuntime）

http go custom 采用标准输出，单条日志大于32k，会自动截断。

第三种：custom-container自定义镜像（CustomImage）

docker 本身会对单条日志进行16k大小的截断。

由于不能控制截断点，所以对于这种场景在资料中说明按照此标准格式最大支持单条的日志大小限制，超过了最大限制导致换行后，默认换行的打印，与正常标准打印一样，即不能够保证关联traceID，或一个traceID里打印重复有串行。
