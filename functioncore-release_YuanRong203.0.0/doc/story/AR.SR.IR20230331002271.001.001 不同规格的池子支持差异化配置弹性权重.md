# AR.SR.IR20230331002271.001.001 不同规格的池子支持差异化配置弹性权重
## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

 不同规格的池子，配置不同的弹性权重，解决大规格池子数量多，占满集群资源的问题。

### 1.2特性场景分析

**当前资源池中每个规格池子大小受以下因素影响产生变动：**
1. worker-manager 启动时初始化资源池，根据 deployments 文件 poolList 配置对每个规格池子大小进行初始化。并创建监听，动态调整池子数量  
2. configmap 中 poolSizeConfig 配置变化，worker-manager 动态感知后调整池子数量，保证每个规格池子数量不小于配置值  
3. 业务流量上涨后，当前的池子资源不满足诉求，会根据需要计算扩容对应规格的池子数量，满足业务的需求。  

**优势与限制：**  
1）根据配置初始化池子的规格数量，并根据配置变化动态感知，可以满足不同业务的最低资源池数量诉求。  
2）流量高峰时扩容对应池子的数量，可以减少对应规格函数冷启动的时延。  
3）在资源有限制的情况下，会出现资源的竞争。特别是大规格函数的大量调用，会导致大规格池子数量多，出现占满集群资源的问题


## 2. 特性/功能实现原理

### 2.1总体方案

需要对资源池的扩容数量上限做限制，可以对不同规格的池子配置不同的弹性权重，限制对应规格资源池扩容的数量上限。

### 2.2模块详细设计

1. configmap 增加不同规格的池子的弹性权重, 并可以动态感知配置变化  

    "poolScaleLimit": {
    	"pool22-0": 0.1,
    	"pool23-0": 0.1,
        ...
    }

2. worker-manager 根据整个集群的资源情况计算对应规格池子数量的扩容上限  
1）集群资源有变化重新计算，调整修改扩容上限值  
2）如果计算的扩容上限值和设置的下限值有冲突，如上限值小于下限值时，以下限值为更高判断优先级  

    以北京四 2000core  内存4000GB 为例：  
        1）512以上规格池子设置上限，默认10%
            pool26-1000-1024-fusion  上限10% 200上限  
            pool24-600-512-fusion    上限10% 333上限  
            pool22-300-128-fusion    上限10% 2000上限 （没有什么意义，不能超过 maxScaleUpPodNums 值 600）
        
        2）下限和上限冲突时，最终pod数以下限为准
            "pool26-0"     configmap 设置下限为250，则最终可以拉起250个pod资源池子

3. 池子扩容时，根据对应规格池子限制的上限值做扩容条件判断   
1）当需要扩容的池子数量超过上限值时，停止扩容资源池  
2）当需要扩容的池子数量未超过上限值时，可以扩容资源池
