# 【GPU商用上线】优化自定义镜像函数磁盘挂载逻辑

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

SD应用中心上线FunctionGraph，完成GPU首批用户商用，在联调过程中发现SD函数冷启动耗时长，原因在于用户配置的磁盘挂载功能是worker在特化阶段才会去执行，而用户是在镜像的entrypoint中执行的磁盘软链，因此存在时延GAP

### 1.2特性场景分析

自定义容器镜像启动~磁盘挂载结束的流程：
1、worker-manager调用K8s接口创建pod，拉起自定义容器镜像（此时entrypoint执行），并等待pod状态ready
2、worker-manager通知vpc-controller插件创建pat-service
3、worker-manager向worker发送特化请求，worker进行vpc路由规则修改之后完成磁盘挂载
4、以上三步完成之后，用户镜像中可以感知到磁盘挂载的目录

时延高的原因：
1、entrypoint的执行是在runtime容器拉起的初始阶段，此时距离磁盘最终完成挂载还有一系列环节，因此需要耗时等待，已确认耗时大头在等待pod状态ready
2、vpc打通是磁盘挂载的必须前提，否则无法完成，而pat-service的创建是秒级的，存在已知性能问题

### 2.2模块详细设计

自定义容器镜像磁盘挂载加速方案：

1、worker-manager在自定义容器镜像pod创建之前申请或创建pat-service
2、在自定义镜像创建时，将vpc相关、磁盘挂载相关所需信息写入worker容器的环境变量
3、worker容器在初始化启动完毕后，若识别到环境变量中存在vpc信息及磁盘挂载信息，则直接进行vpc网络打通和磁盘挂载，无需等待worker-manager的特化请求
4、worker识别到开关开启，则在接收到worker-manager发送的特化请求时，不再二次触发vpc修改和磁盘挂载动作
5、其余特化流程、与worker-manager的交互流程不变

### 2.3 约束

只限于自定义容器镜像场景，其他runtime不受此需求影响

### 3.4可靠性（Reliability）

1、当前之所以先创建pod再创建pat-service是为了减少网卡的无谓损耗，因为当pod创建失败时，无需创建pat-service，且pat-service的删除需要等待1个小时，此方案会对此机制产生冲击（评估影响可控）
2、此场景下worker在执行vpc规则修改和磁盘挂载动作时，可能由于pod未ready导致相关逻辑失败（增加重试机制）
