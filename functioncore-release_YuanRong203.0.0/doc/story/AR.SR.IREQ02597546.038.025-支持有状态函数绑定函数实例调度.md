# 支持有状态函数绑定函数实例调度

关联AR:
+ ARID: AR.SR.IREQ02597546.038.025 

## Story 整体设计

### 功能描述
基于 functioncore 3.0 新架构，有状态函数需要做状态实例私有化，区别于当前的状态共享模式，需要将状态实例和函数实例 1:1 绑定。

### 方案详细设计

#### 现状分析
当前的设计下，状态实例和函数实例不强绑定。

主调调用被调有状态函数时：

  		1. 如果绑定不同的 state 实例进行调度，最终可能会使用相同的实例；
		2. 绑定同一个 state 实例下发多个请求时，最终可能会使用不同的实例。

而这取决于被调函数的实例数量和并发度是否能支撑当前的请求处理。

#### 方案设计

参照当前 requestDispatcher 的设计，有状态函数调度新增 stateReqDispatcher 调度。

结构设计：

```go
type stateReqDispatcher struct {
    scheduler		Scheduler
    scaler			autoscaler.AutoScaler
}
```

proxy 初始化新增 StateDispatcher：

```go
type StateDispatcher struct {
    stateReqDispatchers	map[string]*stateReqDispatcher
    registry		   *servicediscovery.Registry
}
```

* 基本调度流程：

> StateDispatcher 为 proxy 级的调度，有新的有状态函数调度进入，则依据函数的 functionKey 在 StateDispatcher 内判断是否有该函数的 stateReqDispatcher 存在。若存在，则将请求交于对应函数的 stateReqDispatcher 去处理；若不存在，则创建新的 stateReqDispatcher 进行处理。

* 扩缩容流程：

> 区别于当前的扩缩容机制。有状态函数状态实例和函数实例 1:1 绑定，同一个函数绑定同一个状态实例调度时，必须调度到同一个实例上面(实例存在的情况下)，所以只需要维护状态实例 ID 和函数实例的 1:1 绑定关系即可，无需考虑并发调用，实例存在则调度该实例。实例不存在的时候，才需要触发扩容。
>
> 缩容机制保留，有状态函数实例和普通函数实例缩容等待时间一致。

* 异常场景考虑：

> 如果 proxy 异常重启下，缓存内实例信息丢失，重启后会同步 ETCD 数据，进行信息维护。基于此：
>
> * 有状态函数实例，需要在 ETCD 信息里面写入 stateID 数据，用于状态实例和函数实例强绑定。
> * proxy 结构体 workerMetrics 需要增加 stateID，用于数据恢复。

### 约束
1. 实例绑定也是基于扩缩容的基本能力去做的，所以如果一段时间函数不被调用，实例被缩掉以后，状态实例和函数实例的绑定关系也会被重置。
2. 状态实例和函数实例强绑定，即 1:1 关系。函数实例正常存在时，指定同一个状态实例调度同一个有状态函数，调度到同一个函数实例上面处理。
3. 有状态函数不支持预留实例，无法绑定预留实例关系。
