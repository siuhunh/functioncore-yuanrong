# AR.SR.IREQ02793119.004.016 worker在并发条件下用户单条日志过大导致worker发生oom 

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

需求来源于问题单DTS2022081617054转需求 现有状况，现在有3种用户日志采集的情况（rpc/funsion/customImage）worker在并发条件下用户单条日志过大导致worker发生oom，需要将用户单条日志进行拆分成合适大小，多条进行展示，让zapcore及时打印落盘不产生内存堆积

### 1.2特性场景分析

用户日志打印主要场景分析：

第一种： rpc类型的runtime（python、python2、java、nodejs、php、c#）

Runtime -》 worker
worker接收runtime的rpc请求，调用ProcessLog方法，将日志写到Recorder中，最后通过logRecorder.Finish()落盘



第二种fusion类型的runtime（go、http、customRuntime）

runtime-manager的RunProcess方法（在worker目录下），使用STDLogger来收集bootstrap的cmd执行命令信息，通过tcpmsg.ReportLog 将日志发回worker，worker收集日志并在最后的logRecorder.Finish()落盘



第三种custom-container自定义镜像（CustomImage）

worker直接通过监听容器固定路径的日志，调用logger.WriteStdLog方法再以特定的cffagent格式返回，worker收集日志并在最后的logRecorder.Finish()落盘

### 2.1总体方案

由于lts对可保存的日志限制是100K，我们将日志单条拆分为每条90K，参考AWS（也是进行拆分）

### 2.2模块详细设计

第一种： rpc类型的runtime（python、java、nodejs、php、c#）

**需要在每种runtime中对日志进行拆分，再传给worker。这样才可以在各种场景下做到防护（如果放在worker中不可避免的还是会发生内存申请过大的情况导致oom）**



第二种fusion类型的runtime（go、http、customRuntime）

**需要在runtime-manager中对日志进行拆分（只需要修改一处），再传给worker**【需要注意runtime-manager的内存、注意下从runtime获取日志，日志量超过多少的情况会不会存在日志丢失的情况】



第三种custom-container自定义镜像（CustomImage）

**因为docker本身就已经对日志进行截断，还需要在每种worker中对日志进行拆分（docker本身拆分的单条日志长度为16384<90*1024），所以不需要更改**
