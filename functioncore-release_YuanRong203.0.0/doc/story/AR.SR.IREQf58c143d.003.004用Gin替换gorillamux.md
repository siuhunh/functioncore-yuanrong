# 【functioncore】AR.SR.IREQf58c143d.003.004使用Gin替换gorilla/mux

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

gorilla/mux 这款开源软件将在明年二月不被公司cleansource版本火车选型引用，存在不能再使用的风险，并且属于涉A开源依赖；gin是一款 Golang 的微框架，凭借着其封装优雅，API友好，并且不涉及A国，无BCM风险。故需使用gin取代FunctionCore对mux的依赖。并且作为router路由，gin的性能比mux有显著提升。

mux在2023年2月之后进入衰退期，两年未出新版本，将不会引入公司的版本火车。

### 1.2特性场景分析

（1）路由场景：

将url域名的路由转发到handler，并通过request与responseWriter处理请求并返回



（2）获取Request参数场景：

原先的代码逻辑中，使用mux获取请求的参数；现改为通过gin的Context数据结构的Param方法获取所需的请求参数

```go
param = mux.Vars(r) // r为Requests;param未map，再寻找key来获取参数
param = c.Param("key") // Request在c（gin.Context）的数据结构中，使用param方法
```



## 2. 特性/功能实现原理

### 2.1总体方案

使用gin的router，替换httpmuxserver与grilla/mux的router，作为请求的路由方法

使用gin的Context结构数据替换链路上的http.request和http.ResponseWriter，处理请求

使用gin的Context的Param方法来 替换 mux的Vars方法，获取请求参数

### 2.2模块详细设计

涉及到的模块包括state-manager、worker-manager、worker、frontend，涉及到整个链路的调用；涉及到http请求调用的函数，需要做以上总体方案类似的替代，其中包括frontend的clusterhealth检测，frontend的函数触发；state-manager的handler的角色获取方法，创建和删除stateID；worker-manager的健康检查、函数分解、删除函数实例、和上报监控数据的接口路由，以及V1-API的注册；worker模块的http路由都使用gin替换mux。

需要处理参数的时候传带context的接口，其他的保留原形式
