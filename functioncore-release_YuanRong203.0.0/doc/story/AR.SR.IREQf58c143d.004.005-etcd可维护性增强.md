# ETCD可维护性增强

AR：AR.SR.IREQf58c143d.004.005 

## 1. 需求场景分析

### 1.1 特性需求来源与价值概述

1. 路由ETCD故障场景，通过紧急告警，快速识别问题，敏捷感知集群可能的异常状态。
2. 路由ETCD持续故障下，防止暴力切走集群，降低无可用集群风险。

### 1.2特性场景分析

1. ETCD连接性探测，如果连续多次失败，需要上报紧急告警。
2. 路由ETCD业务操作持续失败，需要上报紧急告警。
3. frontend/workermanager和路由etcd持续断连返回集群异常时，需要返回亚健康状态，防止直接暴力切出集群导致集群不可用。

背景：

1. ETCD连接性检测，通过线性读取，以读取是否成功判定连接是否正常。当前连接异常下，只会上报重要告警，不容易被关注到，连接检测持续异常需要升级为紧急告警，供运维快速识别。
2. 路由ETCD业务操作失败，当前无告警，不能快速识别到集群潜在风险。
3. 当前路由ETCD连接性探测持续失败5min后，集群健康检查会上报不可用，导致集群被暴力切走。实际路由ETCD异常情况下，集群大部分场景还能正常运行，暴力切走集群成本过高。此外还存在极端场景，四个集群路由ETCD均不可用下，导致无集群可调度。

## 2. 特性/功能实现原理

### 2.1总体方案

1. 连接性探测：

   1. 新增注册告警类型：etcd检测紧急告警。
   2. 类型注册到紧急告警列表。
   3. etcd连续检测失败10次，上报紧急告警。

2. 业务失败告警：

   1. 新增注册告警类型：etcd业务失败。
   2. 类型注册处到紧急告警列表，类型注册到告警抑制列表。
   3. 当前ETCD业务操作只涉及workermanager写路由信息的操作。失败之后会加入重试列表，在重试列表进行重试时，统计重试失败累计数，每10次触发一次告警上报。

3. 持续失败返回亚健康：

   1. 健康状态新增subhealthy，标记亚健康。

      ```go
      healthy	(subhealthy) unhealthy unknown
      ```

   2. frontend路由etcd持续失联时，状态返回由unhealthy->subhealthy。

   3. workermanager路由etcd持续失联时，健康检查返回错误供上游frontend识别。workermanager 状态由unhealthy -> subhealthy。

## 3. 可信软件

### 3.1安全性（Security） 

*【系统对恶意威胁的防护能力。可能的威胁包括但不限于未授权访问、使用、泄露、破坏、修改、毁灭；防护目标是保持信息的机密性、完整性和可用性】* 

不涉及。

### 3.2韧性（Resilience）

*【系统受攻击时保持在有定义的运行状态（包括降级）、遭遇攻击时快速恢复核心系统、受攻击后在业务需要的时间窗内恢复到有效运行态】* 

功能主要做的是故障下的快速感知识别，以及故障场景下的集群可用性提升。非预防，非自动快速恢复，对韧性提升有限。

### 3.3隐私性（Privacy） 

*【系统具备能力能使客户（含组织和个人）能够就收集、使用、保有、披露和处置个人信息履行其权利和义务】*
不涉及用户敏感数据。

### 3.4可靠性（Reliability）

*【在给定的条件、给定的时间区间能无失效地执行要求的能力】*

亚健康检测识别，防止亚健康状态下暴力切走集群导致集群不可用，对集群的可靠性有提升。

### 3.5可用性（Availability）

*【系统可操作和可访问的程度，或能实现其指定系统功能的概率】*

不涉及。

### 3.6安全（Safety）

*【系统失效导致的危害不存在不可接受的风险，不会伤害自然人生命或危及自然人健康，不管是直接还是通过损害环境或财产间接造成的* 】

不涉及。

### 3.7可维护性

*【系统的可修复(恢复)性和可改进性的难易程度】*

通过增加告警方式，快速感知服务内部与ETCD交互的异常，防止问题发现完，造成影响面扩散，对现网可维护性有较大增强。

### 3.8可测试性

*【代码本地LLT易测试、针对外部接口测试、测试用例具有稳定性】*

LLT：持续故障和亚健康切换需要经过一定耗时，作为LLT测试不合适。

需求上下游耦合度较低，均为单点功能。故障模拟简单，作为可靠性测试点，可测试性较高。

### 3.9性能

*【评估需求本身的性能影响、对其他流程的性能影响】*

相关修改不涉及调用流程修改，对性能影响可控。

*【评估需求对资源的占用，例如go协程，文件句柄、内存、cpu】*

不涉及新增资源占用。
