# 【functioncore】函数资源池动态弹性优化 AR.SR.aae1f193.002

AR： 【functioncore】函数资源池动态弹性优化 AR.SR.aae1f193.002

## 1. Story 整体设计

### 1.1 功能描述

背景：天眼查项目的高流量场景下，对函数资源池的弹性能力提出了更高的要求

功能：需要instanceManager能够评估通信调度带来的负载压力，并将其转化为函数资源池的弹性策略，同时通过扩容请求速率与资源池补充速率，修正弹性幅度

### 1.2 场景分析

- 池子扩容触发条件（已有）：池子使用超过 50%，扩容1/4
- 池子扩容触发条件（新增）：
    - 低负载压力下，资源池补充速率满足扩容速率，池子使用超过 75%，计算扩容1/4
    - 低负载压力下，资源池补充速率不满足扩容速率，池子使用超过 75%，计算扩容2/4
    - 高负载压力下，资源池补充速率满足扩容速率，池子使用超过 50%，计算扩容1/4
    - 高负载压力下，资源池补充速率不满足扩容速率，池子使用超过 50%，计算扩容2/4

- 限制条件：pool池初始大小需要
    - 扩容时限制总的空闲池子个数不能超过 600 个（可配置）
    - 缩容时限制不能缩到初始大小以下

### 1.3 方案详细设计

一、已有弹性能力：

- 涉及参数（默认值）：
  - "usedPodNumsExceedPercentage": 0.5,
  - "scaleUpPodNumsPercentage": 0.25,
  - "extraScaleUpPodNumsPercentage": 0.1,
  - "maxScaleUpPodNums": 600,
  - "thresholdResourceUsage": 0.75

其中：
- usedPodNumsExceedPercentage：触发弹性的阈值，当感知触发门槛过低时，可以调高该值
- scaleUpPodNumsPercentage：弹性的幅度，触发弹性时，扩增的池子规格占原有规格的比例
- extraScaleUpPodNumsPercentage：弹性的上限，触发弹性时，扩增的池子规格不会超过已有的弹性数量加上原有规格的比例
- maxScaleUpPodNums：池子的上限
- thresholdResourceUsage：集群资源的阈值

二、调度策略

当前数据面集群的调度策略分为通信调度（frontend、proxy）和资源调度（instanceManager），其中：
- proxy根据收到的调用请求，根据已有函数实例的处理能力，判定是否需要进行扩容，如果需要，则向instanceManager申请实例（同期需求有优化）
- instanceManager根据配置维护实例资源池，当收到扩容请求时，从池中取出实例并进行特化，再将实例返回proxy

instanceManager当前作为资源调度的核心组件，无法感知通信的负载压力，需要由proxy将相关数据转化为其可识别的指标并随扩容请求传递。

三、指标计算

在现有扩容方案下，对单个proxy来说： 请求总量（M）/函数处理能力（P）= 处理请求需要的实例数（N）
其中，处理请求需要的实例数（N）= 已经存在的实例数（N1）+ 需要扩容的实例数（N2）

1、N1 + N2 与通信负载呈正相关关系
- 即 N1 + N2 = CM，进一步计算得出M 与 N1 / (N1 + N2) 呈正相关
- N1 / (N1 + N2) 的范围为[0, 1]，对应负载策略为：[0, 0.5]为低负载，(0.5，1]为高负载（0.5可配置）
- 当已经存在的实例数为0时，为冷启场景，此时不涉及负载计算，默认低负载

2、采用滑动窗口方式统计60s内扩容请求量，同时统计60s内资源池补充量，窗口大小取10s
计算后分别作为请求速率与补充速率，采用滑动平均方式进行
计算，若感知到补充速率不足请求速率90%时，认为不满足需求。

3、集群资源过载判定机制仍然保留
