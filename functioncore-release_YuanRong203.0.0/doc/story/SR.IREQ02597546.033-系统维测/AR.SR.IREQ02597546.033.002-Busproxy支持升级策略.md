#  Busproxy支持升级策略 

## 1. Story整体设计

### 1. 功能描述
**背景**：

​	为了在保障在现网环境升级时，busproxy业务不中断，请求不丢失且被正确处理完毕

**需求**：

1.  滚动升级，控制按批次升级，避免在升级的过程中业务中断 
2.  收到升级请求时候，去捕获停止信号，不立即进行中断退出，判断业务是否结束，同时设计超时时间，在超时时间内未完成则强制升级
3.  在接收到升级请求的时候，确保不会有新的请求再进来

### 3. 方案详细设计

​	**1. 滚动升级**

 可以在`.spec.updateStrategy.type `配置daementset的更新策略：

- `RollingUpdate`: 这是默认的更新策略。使用 `RollingUpdate` 更新策略时，在更新 DaemonSet 模板后， 老的 DaemonSet pods 将被终止，并且将以受控方式自动创建新的 DaemonSet pods。

```yaml
spec:
  updateStrategy:
    rollingUpdate:
      maxUnavailable: 1
    type: RollingUpdate
```

- maxUnavaible:

  - 升级过程中最多有多少个POD处于无法提供服务的状态，默认值25%
  - 例如：`maxUnavaible=1`，则表示Kubernetes整个升级过程中最多会有1个POD处于无法服务的状态。

  通过配置maxUnavaible，可以保证系统可用的pod数量，保证业务的不间断

2. **更新保证请求处理完毕**

   ​    busproxy的请求主要来自两个地方，一是frontend通过http发送过来请求，二是proxy之间的请求，他们都会经过`HandReq -> doRequest`，因此我们在该处进行请求存量统计，进来+1，返回response时-1。同时记录请求进来时间点，在大于超时时间之后（超时时间900s，可配置 ），进行计数-1，即不再等待该请求。

   ​    pod在升级时候，会接收到 `SIGTERM` 信号，捕获该信号，等待请求存量处理完毕

3. **更新不接收新请求**

   ​	对于新请求，在接收到升级信号之后，来自frontend和busproxy的请求都要进行关闭。

   **来自frontend请求**

   functiontask在启动时候会将节点信息注册到etcd，供frontend进行服务发现调用，就可以在接收到 升级`SIGTERM` 信号之后，将该节点的etcd信息删除，使frontend的请求不再发送到该节点。

   **来自busproxy 的请求**

   ​	如果Busproxy当前处于升级状态，则再接收到其它busproxy请求则进行升级失败返回 ，在接收到该失败返回之后则不再发送给该实例。即在`HandReq -> doRequest`接收到升级信号之后拒绝新的请求处理。

   ​	被拒绝请求进行重新发送，并且不再发送给该节点。
